# 真实网关接入案例：new-api 系中转

一份完整的新网关接入实录，来自本 skill 的开发过程。接入任何新上游时，
可按同样的取证顺序走一遍。网关地址已隐去，方法可复用。

## 一、连通性探测

对目标网关（new-api 系中转，HTTPS + 非标准端口）的验证结果：

| 探测项 | 结果 |
|---|---|
| DNS / TLS | 正常，证书有效 |
| `POST /v1/messages` | 路径有效，返回 `Invalid token`（缺令牌时） |
| `POST /v1/chat/completions` | 该网关同时提供 OpenAI 原生路由 |
| `/api/anthropic/v1/messages` | 不存在，返回 `Invalid URL` |

判断网关类型的依据三条：

1. 网关错误格式为 `new_api_error`，是 new-api 系网关
2. 缺令牌时 `/v1/messages` 返回 `Invalid token` 而非 `Invalid URL`——说明请求
   已进入 relay 环节，路径本身是对的
3. 该网关还暴露了 OpenAI 原生路由

「缺令牌时报 token 错而非 URL 错」这个细节能区分路径配置错误与鉴权错误，
探测新网关时优先看这一点。

## 二、双路由的两种用法

同一家 new-api 网关可能同时提供 Anthropic 兼容路由与 OpenAI 原生路由：

1. 走 Anthropic 协议转换，即本 skill 脚手架的默认配置；
2. 若令牌也被允许调用 OpenAI 路由，可直接把它当 OpenAI 端点用，跳过本地代理。
   脚手架的 `detect.bat` 会自动探测并给出结论。

补充：new-api 系网关偶发 CPU 过载会返回 `system cpu overloaded`（HTTP 401/503），
它和令牌无效的错误码相同但文案不同，别误判成配置错。重跑即可。

## 三、glm-5.3 五项端到端实测

配置生效后，用真实令牌跑通了全部五项：

| 能力 | 结果 | 实测表现 |
|---|---|---|
| 模型列表 | PASS | 网关返回 24 个可用模型 |
| 非流式对话 | PASS | system 正确提升，usage 正常返回 |
| 流式 SSE | PASS | 约 340 个分片，首字节约 9 秒（含思考耗时） |
| 工具调用 | PASS | `get_weather({"city":"杭州"})`，参数合法、结果可回传 |
| 多模态输入 | 链路通、内容不可靠 | 累计 17 次测试中约 10 次正确，可用率约 60% |

## 四、多模态劣化的定位过程

多模态这一项必须单独说明。图像确实能被送达模型——模型会给出具体的颜色判断，
说明它「看」到了画面；但准确率约 60%，同一张图重复提问会给出不同答案，
错误答案集中在红色方块的邻近色（黄、橙）。这意味着图像特征被部分劣化，可能是
中转网关在转发时对图像做了压缩或重采样。

累计实测数据：17 次请求中识别正确约 10 次，其余 7 次答成邻近色或回答未看到图片。

结论：不要把这个端点用于依赖精确图像识别的场景。做 OCR、图表读数、
验证码之类任务时需要人工复核。

排查多模态问题时有两点值得先排除：

1. 思考块吃 token：模型先产出思考块，`max_tokens` 给太小（如 100）会被思考耗尽
   导致正文为空，此时并非链路故障，调到 1000 以上即可
2. 责任归属判定：用 curl 直连上游对比——若直连同样识别错误，问题在网关或模型侧，
   与本地协议转换无关（本案例中直连结果同样不稳定）

## 五、同网关多模型能力差异（另一个佐证）

同一网关背后挂着不同厂商的模型，能力差异极大（详见 `pitfalls.md` 第 11 条）：
deepseek 系列要求删 `type: custom` 才不 422；MiniMax-M2.7 三张纯色图 0/3；
M3 全对；输出上限从 131072 到 524288 不等。能力字段必须逐模型实测，见
`scripts/probe_model_caps.py`。
