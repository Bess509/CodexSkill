# Codex 规划验收，Claude Code 执行

## 分工与边界

- Codex 负责需求澄清、业务概念解析、计划、任务派发、独立验收、返修要求和最终报告。
- Claude Code 负责被派发任务中的实现、文件修改和获准命令；报告改动、执行证据和阻碍，不自行决定验收通过。
- 不默认由 Codex 接手实现。Claude 不可用或无权执行时，报告具体阻碍；只有用户同意改变分工后才改用其他执行方。
- 授权不因委派而扩大。沿用当前任务的操作范围和审批边界；本 Skill 不授予部署、删除业务数据、发送消息等额外权限。已有授权无需重复询问。
- 使用本机 Claude Code CLI，保留现有认证与模型配置，不修改 Base URL、密钥、登录方式或默认模型。不要把密钥写入任务单、Skill 或报告。

## 1. 建立任务与业务上下文

1. 确认项目绝对路径、目标、现状和用户已有改动；读取适用的 AGENTS.md、CLAUDE.md 及项目规范。缺少项目路径时先定位，无法定位才询问。
2. 读取 [reference/index.md](reference/index.md)，只加载匹配当前业务的概念文件。没有已登记业务时，依据用户与项目证据工作，不把模板当作真实定义。
3. 将业务概念转为可检查的规则：字段含义、状态转移、金额/时间/数量口径、边界值、示例和证据来源。概念缺失仅在影响结果时询问；其余假设记录在计划中。
4. 使用任务现有的产物约定。在无约定时，于项目 `work/codex-claude/<run-id>/` 保存过程记录，于 `outputs/` 保存最终交付和报告；不把过程文件误计为业务改动。
5. 建立 `plan.md`，包含任务分解、允许修改范围、禁止改动范围、业务文档版本、验收条件、验证方法和初始检查点。对已有 Git 工作区记录初始差异；无 Git 时对相关文件做必要快照或哈希，保护用户已有改动。

## 2. 交给 Claude 执行

按可独立验收的单元派发任务，避免两个执行会话同时修改相同文件。

- 从 [assets/executor-task.md](assets/executor-task.md) 生成任务单，明确项目绝对路径、输入、输出、允许修改的文件、业务规则、验收条件和获准命令。把需要的业务概念摘录进任务单并保留来源，或在任务范围内提供对应文件。不要假定 Claude 能看到本聊天或 Skill 目录。
- 返修时生成新的任务单：保留原目标，附上失败条件、可复现证据及禁止退化的已通过条件；不要只转发“没通过，继续修”。
- 执行前读取 [CLI 调用与权限](reference/cli-execution.md)，核对本机参数与继承配置。Windows 使用随附脚本，一次调用对应一次执行记录；其他平台按参考文件适配。
- 默认仅开放 Read、Glob、Grep、Edit、Write。命令工具必须显式启用，并先核查继承权限；自动批准列表不构成命令或文件路径的隔离边界。无法确认范围时不要开放命令工具，报告具体限制。

## 3. Codex 独立验收

每轮执行完成后，Codex 依据实际产物验收，并用 [assets/review-and-report.md](assets/review-and-report.md) 记录结果：

1. 对照初始检查点检查文件、差异和产物，确认实现范围、用户已有改动和业务规则。
2. 独立运行与改动匹配的检查或测试，保存命令、退出码和关键结果。Claude 的自测记录可作线索，不能替代独立验证。文件内容可直接断言时不必新增形式化测试。
3. 按验收条件逐项给出 `PASS`、`FAIL` 或 `NOT_RUN`，附可定位证据。检查是否通过删测试、放松断言、硬编码示例或改验收标准掩盖失败。
4. 未执行的关键检查不能标为通过。进程退出码 0、CLI `is_error=false` 或 Claude 自称完成，都只表示执行情况，不等于业务验收通过。

Codex 的复核命令应以验证为目的，避免带自动修复副作用的参数。需要修复实现时交还 Claude；执行过程确有格式化或生成文件需求时写进任务单。

## 4. 返修循环与停止条件

状态流：`PLANNED → EXECUTING → REVIEWING → ACCEPTED`；有可修复问题则 `REVIEWING → REPAIRING → EXECUTING`。

- 存在可执行的修复路径且仍在原范围内时继续返修，无需每轮重复征求许可。每轮任务单、执行结果、验收记录均保留，不能覆盖前轮证据。
- 默认同一任务最多进行 **5 轮 Claude 执行（含首次）**。某条失败条件在 **连续 2 轮返修后仍无实质进展**，先由 Codex 重新定位原因；同一阻碍仍无法推进时停止该循环并报告。用户指定的次数或预算优先。
- 密钥/额度/网络不可用、必要权限被拒绝、业务定义冲突且必须由用户决策时，不空转重试；先完成不依赖该条件的工作，再清楚说明所需输入。
- 单次时限覆盖任务输入、执行和输出读取；超时后进行有限时的进程清理。检查已落盘修改、清理结果与仍运行的进程，确认状态后再派发；超时不证明工作区无变化。
- 预算或轮次耗尽时报告 `INCOMPLETE`，环境/决策阻碍报告 `BLOCKED`；这只是本 Skill 的报告标签，不替代宿主的 goal 状态规则。不得为了结束而标记 `ACCEPTED`。

## 5. 最终报告

由 Codex 编写，包含：结论、计划完成情况、最终产物、改动范围、业务概念来源、逐项验收与证据、执行/返修轮次、未验证项和剩余限制。使用 [assets/review-and-report.md](assets/review-and-report.md) 的最终报告部分，按任务规模删减。

文件型报告保存为 `outputs/<run-id>-report.md` 或用户指定位置，聊天给出结论和链接。只有所有必要条件通过且无必需工作遗留时，结论才为 `ACCEPTED`。

## 扩展入口

- 新业务：在 `reference/<domain>/concepts.md` 存储定义，并登记至 `reference/index.md`；结构参照 [reference/business-concepts.template.md](reference/business-concepts.template.md)。按需增加该业务的 `rules.md`、`examples.md`，不要让通用流程包含某行业默认规则。
- 新验收方式：把真实项目的检查命令、断言和证据格式写进业务文档或项目规范，并编入任务单验收条件；不更改“Codex 最终裁定”的分工。
- 新执行环境：扩展脚本或增加适配器，维持任务单输入、执行结果与元数据输出，验收和报告仍由 Codex 完成。
- 新项目偏好：在项目 AGENTS.md 或任务说明中指定业务域、输出目录、模型、轮数与预算；不要把单一项目的配置写死到全局 Skill。
